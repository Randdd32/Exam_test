Вот общие требования к приложению, которые будут на экзамене. Им всем нужно соответствовать:
2. Общие функциональные требования (для всех вариантов)
2.1. Аутентификация и авторизация
Регистрация нового пользователя (логин, пароль, email).
Вход в систему (логин/пароль).
Выход из системы.
Доступ к основным операциям только для аутентифицированных пользователей (публичные страницы – только вход/регистрация и, возможно, просмотр общедоступных данных, если это предусмотрено вариантом).
2.2. Модель данных и бизнес-логика
Доменная модель должна содержать минимум 4 сущности.
Обязательно использование связей «один-ко-многим» и «многие-ко-многим». (многие-ко-многим может быть с доп атрибутом, как это в варианте интернет-магазина).
Бизнес-логика должна быть выделена в отдельные классы/модули (сервисы), а не располагаться в контроллерах или представлениях.
Для взаимодействия с пользователем (передача данных между сервером и клиентом) необходимо использовать DTO (Data Transfer Objects).
2.3. CRUD-операции
Реализованы операции создания, чтения (список и детали), обновления и удаления  для всех основных сущностей (в рамках варианта). Для связующих сущностей (таблиц связей) CRUD может быть частичным (например, только создание и удаление). И для связующих сущностей в идеале прямо внутри круда главной сущности сделать это. Как-то либо модальным окошком с множественным выбором, либо списком с множественным выбором, либо еще как-то, как удобнее будет.
2.4. Фильтрация и поиск (на двух страницах как минимум)
Страница А – список объектов, принадлежащих текущему пользователю (например, «Мои заказы», «Мои заметки», «Мои посты»). На этой странице реализованы:
поиск по текстовому полю (название, описание и т.п.);
фильтрация по категории / тегу;
фильтрация по диапазону дат (если применимо) или по значению числового поля (например, цена, размер).
Страница Б – публичный список объектов (всех пользователей или общедоступных). На этой странице реализованы:
поиск по названию / заголовку;
фильтрация по автору / владельцу (частичное совпадение имени или выбор из списка);
ещё один дополнительный фильтр (по тегу, по цене, по дате – в зависимости от варианта).
Фильтрация и поиск должны выполняться на стороне сервера (через параметры запроса), результат должен обновляться без полной перезагрузки страницы.
2.5. Валидация данных
На клиенте: все поля форм проверяются перед отправкой (обязательность, минимальная длина, корректный формат email, пароль корректного формата и т.д). И тут надо бы не как у меня в дипломе, когда просто выводится тост при проверке полей форм, а если возможно, использовать инлайн-валидацию. То есть подсветка поля + текст под ним.
Практические советы для UX:
Не будьте агрессивны: Не делайте поле красным до того, как пользователь начал взаимодействие с ним. Если пользователь только зашел на страницу, красные поля выглядят как ошибка системы. Включайте подсветку либо в момент потери фокуса (onBlur), либо при попытке отправить форму.
Не прячьте кнопку: Если кнопка «Отправить» неактивна при ошибках, пользователь может не понять, почему она не работает. Лучше оставить кнопку активной, но при нажатии подсвечивать все поля с ошибками и скроллить к первому из них.
Сочетайте: Если при нажатии «Отправить» форма выдает ошибку сервера, покажите пользователю тост («Что-то пошло не так, попробуйте снова») и одновременно с этим оставьте текст под полем, чтобы он видел, что именно в данных ему нужно поправить.;
валидация на сервере: входящие данные обязательно проходят валидацию, неккоректные запросы отклоняются с кодом 400 и возвращают понятное сообщение об ошибке.
На сервере: входящие данные обязательно проходят валидацию, некорректные запросы отклоняются с кодом 400 и возвращают понятное сообщение об ошибке.
2.6. Пользовательский интерфейс и требования к вёрстке
Приложение должно содержать не менее трёх функционально различных страниц (например: вход/регистрация, страница со списком №1, страница детального просмотра/создания, страница со списком №2). Точный набор страниц зависит от варианта.
Адаптивная вёрстка: страницы должны корректно отображаться на экранах шириной от 320px до 1920px (использовать flexbox, grid, медиазапросы, фреймворки и т.д.).
Обратная связь: при выполнении длительных операций (загрузка списка, сохранение) должны отображаться индикаторы загрузки; при ошибках – понятные сообщения; при успешном выполнении – уведомления (например, всплывающие сообщения или изменение интерфейса).
Навигация должна быть интуитивной, все основные сущности доступны через меню или ссылки.
2.7. Технические требования
Использование системы сборки (для SPA – Vite или Webpack).
Линтер (ESLint) для проверки кода на JS/TS.
Код должен быть структурирован, читаем, с осмысленными именами переменных и функций. (еще логику на самих файлах страниц (на фронте) нужно стараться минимизировать, вынося все в отдельные хуки и сервисы).
Данные должны сохраняться между запусками приложения (файловая база, SQLite, PostgreSQL, MySQL – на выбор студента).
Серверная часть должна реализовывать корректные HTTP-методы (можно: GET, POST, PUT, PATCH, DELETE, не обязательно сразу все) и возвращать соответствующие коды ответа.
Примечание: в каждом варианте студент может добавить дополнительные атрибуты и сущности по своему усмотрению, если они не противоречат основным требованиям.

Для всех операций (включая фильтрацию) предусмотрены индикаторы загрузки и понятные сообщения об ошибках.
